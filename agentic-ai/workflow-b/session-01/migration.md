# Workflow B, session 01: Migration plan (for human review)

Status: **draft for review. No migration work starts until the human approves.**
Inputs: `Investigation.md` (same folder). Baseline gates: 354 passing / 0 failing, typecheck 0 errors, smoke 13/13.

## 1. Goal and non-goals

* Convert the 169 convertible files (`server/**` minus `server/libs/**` and the 15 Umzug scripts in `server/migrations/`, plus `index.js`, `prod.js`) from JS to TS, **in dependency order, in small verified batches**.
* The runtime stays CommonJS and the behaviour stays the same. No refactors beyond what typing forces.
* Tests are never edited to make them pass, and never skipped, weakened or deleted. No `@ts-nocheck`, `@ts-ignore` or `@ts-expect-error`. No blanket `any`.
* Non-goal: converting everything regardless of quality. Partial coverage, reported honestly, beats a full conversion with doubtful evidence.

## 2. Toolchain design (built in session 02, verified there)

| Item | Decision | Why |
|---|---|---|
| Emit strategy | `tsconfig.build.json`: `extends` tsconfig.json, `noEmit:false`, `allowJs:false`, `noCheck:true`, `include: ["index.ts","prod.ts","server/**/*.ts","types/**/*.d.ts"]`, exclude `server/libs`. Emits each `foo.ts` to a sibling `foo.js` | All `require` paths, test paths, `__dirname` paths, `pkg.scripts` and the MigrationManager file copy keep working. Prototype verified with TS 7.0.2 |
| Type gate | the existing `tsconfig.json` (`allowJs`, `noEmit`) + `npm run typecheck` | It type-checks TS against the not-yet-converted JS, and it prefers `.ts` over a generated `.js` (verified) |
| Class fields | add `"useDefineForClassFields": false` to tsconfig.json | Keeps JS assignment semantics. No own `undefined` properties (verified in the prototype) |
| Scripts | `build:server` = `tsc -p tsconfig.build.json`; `build:watch`; `pretest`, `prestart`, `predev` → `npm run build:server`; `clean:ts` = small node script that deletes generated `.js` that has a sibling `.ts` | `npm test`/`npm start` (and therefore measure.sh/smoke.sh) always run current code |
| Generated files | `.gitignore` block `# --- generated by tsc (workflow-b) ---` with one explicit path per converted file, added in the same commit that converts the file | An explicit list never hides a new hand-written `.js`. Easy to audit |
| Deploy | Dockerfile build-server stage: also copy `tsconfig*.json` + `types/`, then `npm ci && npm run build:server && npm prune --omit=dev` instead of `npm ci --only=production`. CI pkg job: `npm ci && npm run build:server` before pruning/packaging | Otherwise the image has no `.js` for converted files. **Cannot be verified locally; flagged for the human** |
| Strictness | Project tsconfig stays `strict:false` while the migration is mixed. Each new `.ts` is **written to pass strict mode**, checked per batch with an informational strict check of only the converted files (the same reference config as measure.sh, using the pinned compiler) | Raising project strictness on JS would flood the gate with errors that are not part of the migration. Measuring strict errors on the converted files keeps quality visible |
| Untyped packages | add pinned `@types/*` devDependencies (passport, passport-jwt, express-session, cookie-parser, nodemailer, semver, xml2js) only in the batch that first imports them from TS. Otherwise write a minimal `types/<pkg>.d.ts` | Avoids TS7016 under strict, with no speculative dependency churn |

## 3. Conversion recipe (applied to every file)

1. `git mv x.js x.ts` (keeps history), then edit.
2. Imports:
   * whole-module require → `import X = require('...')` (builtins, packages, first-party);
   * destructured **first-party** require → `import modX = require('./x')` + `const { a, b } = modX` (keeps the load-time snapshot semantics);
   * destructured **package/builtin** require → `import { a } from 'pkg'` is acceptable only where a load-time snapshot vs live binding cannot matter (immutable package exports such as `sequelize`'s `DataTypes`/`Op`); otherwise use the snapshot form;
   * requires that are only used for JSDoc (`const { Request } = require('express')`) → `import type`;
   * lazy requires stay lazy: `const X: typeof import('./X') = require('./X')`. This is a typed declaration, not an assertion, because `require` returns `any`. If that ever fails, note it in evidence;
   * type-only use of a module that would create a new runtime edge → `import type X = require('...')`.
3. Exports: keep the exact runtime shape. `module.exports = X` → `export = X`; `module.exports.a = …` sequences → one `export = { a, … }` object at the end, preserving any internal `module.exports.a()` routing via the named object. Cross-file types go in a merged `namespace X { export interface … }` (type-only, emits nothing) or in `types/shared.d.ts`.
4. Classes: declare every field with its type. In Sequelize models, every attribute is `declare`d and the no-op `this.x` constructor lines are removed. Nothing else in the constructor changes.
5. JSDoc types move into the signatures. Descriptions stay. Each JSDoc type is checked against the actual use, not copied blindly.
6. Unknown input (`req.body`, `JSON.parse`, metadata from files, HTTP responses) → `unknown` or a declared interface, narrowed where it is used. Scoped `as` assertions are allowed only at genuinely dynamic boundaries (`sequelize.models.x`, `Error().stack`), each with a short comment.
7. Do not change logic. If typing reveals a real bug, record it in evidence and **leave the behaviour as it is** (a bug-fix needs a separate human decision).
8. After the build, diff each emitted `.js` against the original JS (`git show HEAD:path.js`), ignoring whitespace/comments, as a sanity check that only types were removed and `"use strict"` added.

## 4. Batch-size rule

* **Pilot phase (sessions 02 to 03):** at most 5 files or 600 lines per session, plus the toolchain change in session 02.
* **Growth:** after **two consecutive sessions with all gates green on the first full run** and no recipe change, the limit goes up to 12 files or 2,500 lines, grouped by dependency level and area. After two more clean sessions it may reach 20 files or 4,000 lines.
* **Caps that always apply:** a file over 1,000 lines counts as its own batch (at most 2 small companions). Untested areas (scanner, queries, models, controllers) never exceed 8 files per session. Only one cycle sub-group per session.
* **Shrink rule:** if a session needs more than one fix-and-rerun cycle on the test gate, or reverts any file, the next session goes back to the previous size.

## 8. Rollback approach

* **Within a session:** if a file cannot pass the gates without changing behaviour or weakening types beyond the policy, put it back (`git restore --staged --worktree` on the `.ts`, then `git checkout HEAD -- x.js`, remove the generated `.js` and its `.gitignore` line). Mark it deferred, with the reason, in evidence.md. The rest of the batch can still be committed if it is green.
* **After a session:** each session is one commit (`workflow-b session NN: <summary>`), so `git revert <sha>` cleanly undoes one batch. History is never rewritten and nothing is pushed.
* **Toolchain:** if the in-place emit approach fails in session 02 (e.g. tests or smoke cannot see the generated JS), revert session 02 and come back to the human with alternatives before going further.
